## 2. Stack & deployment
- **Framework**: Vite 7 + React 18 + TypeScript 5.5, `react-router-dom` v6 in **HashRouter** mode (so `/chapters/:id` works on GitHub Pages without server config).
- **PWA**: `vite-plugin-pwa` with autoUpdate, Workbox precache for `**/*.{js,css,html,svg,ico,png,woff2}`. Manifest declares day/night SVG icons; theme-color is flipped at runtime in `App.tsx`.
- **Storage**: Dexie 4 → IndexedDB DB `wayfare`, two stores: `entries` (++id, date, chapter_id, challenge_id) and `settings` (single row, id='family'). No backend, no sync.
- **Markdown render**: `react-markdown` + `remark-gfm` + `rehype-raw` + `rehype-sanitize` (custom schema allows `class` attribute on every element so the embedded `<div class="vibe vibe-egypt">…` and `<div class="tongues">…` blocks survive sanitisation).
- **Content loading**: `import.meta.glob('../../../content/chapters/**/*.md', { eager: true, query: '?raw', import: 'default' })` in `app/src/lib/content.ts`. Same trick for `deck.yaml`. Everything is inlined at build time; the PWA is fully self-contained.
- **Vite config**: `base: './'` (relative URLs work whether served from `/` or `/wayfare/`), `server.fs.allow` includes `../content/`, alias `@content` → `../content`.
- **Build & deploy**: `.github/workflows/pages.yml` runs on push to `main` (and one feature branch). It runs `node scripts/build-printables.mjs` first (writing into `app/public/printables/`), then `npm run build` (which is `tsc -b --noEmit && vite build`), uploads `app/dist/` as the Pages artefact, deploys to `angrezibahu.github.io/wayfare/`.
- **Tests**: Vitest. One unit test for `resolveUnlock`, one for astronomy. No UI tests.
## 3. How content is currently stored
### 3a. Chapters — markdown with YAML front-matter
22 files at `content/chapters/<season>/<slug>.md`. Every chapter has:
```yaml
---
id: orion
title: Orion
kind: sky | land           # roughly "what kind of skill" — NOT day/night
season: always | winter | spring | summer | autumn
unlock:
  always: false
  season: winter
  prerequisite: moon       # chapter id
  field_trigger:
    any_of:
      - type: sighting_logged
      - type: challenge_completed
        challenge_id: find-orions-belt
sources:                   # free-text strings (mix of cultures and book titles)
  - Greek mythology
  - Yolŋu people of Arnhem Land (Australia) — referenced, not taught
  - Arabic astronomy (star naming)
---
Body is freeform markdown. The shape follows the manifesto's five-part arc, with per-chapter optional sections:

## Story — story from a named tradition (often several, one per culture)
## Sky or ## Land — how to find / read it
## Five tongues for one X — multilingual <dl> table inside <div class="tongues"> (Old English / Scots / Welsh / Irish / Hindustani is the recurring set)
## Historical — three ways of … — three civilisations side by side, each in <div class="vibe vibe-{egypt|greece|japan|ww2|modern}">
## Science
## Skill — …
## Try It — wayfaring from the historical pages — one or more <div class="vibe vibe-try"> activity blocks
## Stretch — Challenges — numbered list, each item self-grades Starter | Core | Stretch
## Further — books / sites / orgs as plain bullets (no structured links)
3b. Challenges — single YAML file
content/challenges/deck.yaml holds all 33 cards under cards:. Each card:

- id: find-orions-belt
  title: Find Orion's Belt
  grade: Starter | Core | Stretch
  kind: Sky | Land | Story | Error
  provenance: short string
  time: short string
  prompt: |              # multi-line markdown
  fieldbook_prompt: |    # multi-line markdown
  unlocks:               # optional, list of chapter ids
    - orion
3c. Sky objects, ground objects, "Try-It" experiments — NOT modelled as data
These exist only as prose inside chapter bodies and (in one case) as a hardcoded TS object:

Constellations (Orion, Cassiopeia, Cygnus, Pegasus, Ursa Major, Leo, Boötes, Scorpius, Taurus, Canis Major, Lyra-Aquila-Cygnus combined as Summer Triangle…) — only as chapter ids and as bold/heading text inside chapter bodies.
Stars (Betelgeuse, Rigel, Sirius, Aldebaran, Vega, Deneb, Altair, Antares, Polaris, Regulus, Arcturus, Spica, Albireo, Mizar/Alcor, Alpheratz, Markab, Scheat, Algenib, Schedar, Caph, Ruchbah, Segin, Shaula, Lesath, Denebola, Phecda, Merak, Dubhe, Megrez, Alkaid, Alioth…) — only as bold text inside chapter bodies. Their cross-cultural names ("Betelgeuse / Yad al-Jauzā' / hand of the Central One") are explained inline.
Cross-cultural names (Ursa Major / Saptarshi / The Plough / Meskhetyu / Mi'kmaq celestial bear hunt) — repeated by hand in each chapter that touches them.
Ground objects (sastrugi, holloways, drystone walls, oxbow lakes, contour lines, tracks, cloud genera, rainbows, frost lines, tree-leans, rip currents, Nilometers…) — only as prose.
Try-It experiments (Egyptian merkhet plumb-line for Polaris, MI9 floating-needle compass, garden Nilometer, paper Tower of the Winds, sounding a stream RN-style, Eratosthenes shadow…) — embedded as <div class="vibe vibe-try"> blocks inside chapter bodies. Some of these are also deck cards (Shadow Stick at Noon, Pace-Count, Eratosthenes Match), with the prose duplicated by hand.
Featured constellations on Tonight's Sky — hardcoded FEATURED record in app/src/lib/astronomy.ts keyed by season → {id, title, where, signpost, window}. This duplicates info that could be derived from chapter front-matter. Chapter id strings here must be kept in sync with chapter files manually.
3d. Fieldbook templates — SVG files
8 numbered SVGs at content/fieldbook-templates/: title, moon-diary-month, sky-log, constellation-study, landcraft-log, error-journal, story-of-this-place, year-map. The build script wraps each in a print-and-share HTML shell and emits app/public/printables/<stem>.html, plus fieldbook.html (bundle) and index.html (catalog). No metadata file; the script discovers SVGs by glob and humanises the filename for the title. No back-link from a template to the chapter it belongs to.

3e. Fieldbook entries — IndexedDB only
User-generated. Schema in app/src/lib/db.ts. Each entry: {date, body, author?, chapter_id?, challenge_id?, tags?}. Exportable as markdown. Never leaves the device.

6. Inconsistencies / drift I noticed
These are flagged so the data model can normalise them, not for fixing now:

Dangling challenge_id references. Several chapter front-matters point at challenge ids that don't exist in deck.yaml:
ursa-major references find-polaris — deck has first-pole-star-sighting.
leo references find-the-sickle — not in deck.
bootes-arcturus references arc-to-arcturus — not in deck.
summer-triangle references find-the-summer-triangle — not in deck.
scorpius-antares references find-antares — not in deck.
milky-way references dark-sky-milky-way — not in deck.
pegasus-andromeda references find-the-great-square — not in deck.
cassiopeia references find-the-w — not in deck.
cygnus-revisited references northern-cross-sets — not in deck.
The unlock resolver silently treats these as never-satisfied; the sighting_logged branch in any_of saves the user.
kind is not day/night. reading-the-sky-by-day has kind: sky but is a daytime chapter. kind is really "is this a sky-skill or a land-skill", not when of day it applies.
In-chapter Stretch lists vs deck cards are partly duplicated by hand (e.g. Shadow Stick at Noon appears as deck card shadow-stick-at-noon and in landcraft-first-steps Stretch list).
Try-It experiments have no IDs. They're prose blocks. Some of them (Eratosthenes, Floating-Needle Compass, Merkhet Night, Polaris by Plumb-Line) are also mentioned in Stretch lists as if they were deck cards; the lists call them "Deck card" but the deck doesn't actually contain them yet.
Sources mix cultures, books, and "referenced, not taught" annotations in a single string array.
Featured constellation duplicated between FEATURED in astronomy.ts and the chapter front-matter / curriculum doc.
7. Open questions (please answer before I implement the model)
Does the proposed day_or_night field replace kind, or live alongside it? I think we want both: kind: sky | land (skill-axis) and day_or_night: day | night | either (when-it-applies-axis). Confirm.
Should unlock rules survive into the new model unchanged, or do you want to fold them in? The proposed minimum fields don't mention unlock; if you want season-gating to keep working we need to keep the unlock block as a separate sub-object.
Cultures vocabulary — closed enum (celtic, hindustani, greek, arabic, egyptian, norse, chinese, japanese, polynesian, māori, aboriginal-australian, inuit, sami, mi-kmaq, san, babylonian, british-folk) or freeform strings? I'd recommend a closed enum with a referenced_only: true flag so we never accidentally treat "Yolŋu — referenced, not taught" as teachable.
Themes vocabulary — same question. Suggest closed enum (science, language, folktale, history, instrument, safety, error-curriculum, seasonal-clock, wayfinding, weather).
Where should the new sibling tables live? Two clean options:
(a) JSON/YAML index files at content/sky-objects.yaml, content/ground-objects.yaml, content/experiments.yaml, content/printables.yaml. Easiest to read and version-control. My recommendation.
(b) Per-object markdown files at content/sky-objects/orion.md etc. with their own front-matter, mirroring the chapter pattern. Heavier but lets you write essays per object.
Backfill scope. For this first pass, do you want me to:
just define the schemas and one or two worked examples, or
extract every named star / constellation / experiment from the existing chapter prose and populate the sibling tables fully?
The second is meaningfully more work and benefits from a second review pass.
Source-link note field — should source_links carry a culture tag (so a book about Mi'kmaq astronomy is linked to that culture) or stay neutral? My recommendation: optional cultures: [] on each source link, since Hawaiki Rising is a Polynesian source but Star Tales isn't culture-specific.
Experiment ⇄ challenge-card relationship. A Try-It block and a deck card can describe the same activity (Eratosthenes, Shadow Stick). Do you want them merged into a single experiments table that the deck draws from, or kept as parallel tables linked by id?
Printables: do we want a printables.yaml index, or a single front-matter block at the top of each SVG (as XML metadata)? YAML index is simpler and survives Inkscape edits.
Should the model be enforced (build fails on dangling ids) or advisory (warnings only)? Recommend enforcement for chapter↔card↔object refs once the model lands, since the dangling-id list above is exactly the kind of drift that compounds.
